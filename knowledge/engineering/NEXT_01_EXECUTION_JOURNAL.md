# P0 — серверный журнал исполнения и приёмки

**Статус:** ТЗ для следующей разработки; не утверждение, что уже реализовано. **Зависит от:** существующего учебного наряда `backend/order-preview.mjs`, `backend/governance.mjs`, локального реестра `backend/registry.mjs`. **Существующее поведение сохранять.**

## Зачем

Должна существовать проверяемая цепочка: основание поручения → выдача → начало → отчёт исполнителя → проверка инспектором → решение заказчика → архив/спор. Техническое подтверждение и финансовая приёмка не равнозначны; фактический процесс уточнить у заказчика.

## Модель данных (проект)

- `work_orders`: `id`, `asset_id`, `network_version`, `operation_type`, `contract_ref`, `contract_version`, `issuer_id`, `assignee_org_id`, `resource_refs`, `planned_start`, `planned_end`, `status`, `created_at`, `version`, `simulation_mode`.
- `work_order_events` — **append-only**: `id`, `order_id`, `seq`, `event_type`, `actor_id`, `actor_role`, `occurred_at`, `recorded_at`, `payload_json`, `idempotency_key`, `evidence_refs`. Правки событий запрещены; исправление — новым событием со ссылкой на исходное.
- `evidence_attachments`: `id`, `order_id`, `sha256`, `filename`, `mime`, `size`, `storage_ref`, `visibility`, `submitted_by`, `created_at`; файлы — не напрямую в общедоступный каталог.
- `order_reviews`: результат осмотра/замечание/требование повторной работы, отдельное решение заказчика. Хранить ссылку на норматив или договор при наличии.

## Переходы статусов — согласовать с заказчиком

`draft -> issued -> started -> reported -> inspected -> accepted`; `inspected -> needs_rework -> started/reported`; отдельные ветви `rejected`, `cancelled`, `disputed`. Никогда не «пропускать» исполнение, осмотр или утверждение простым нажатием в UI, если такая проверка обязательна в выбранном процессе.

## Права

- `dispatcher`: черновик/выдача/переназначение только в полномочиях; не может сам принять свою работу.
- `executor`: начало, фото/документы, отчёт по назначенным заданиям.
- `inspector`: осмотр и замечания, но не подмена полномочий заказчика.
- `customer`: решение о приёмке/возражениях в пределах договора.
- Роль должна устанавливаться **серверной аутентификацией**, а не доверяться `role` из JSON запроса. Локальные демо-роли — строго `simulation`.

## Инварианты, которые нельзя нарушить

1. Смена/договор/участок/операция фиксируются на момент выдачи; ссылки на версии неизменны.
2. Принятие невозможно без допустимой последовательности событий и полномочий.
3. Принятие не выводится из GPS или отметки «пройдено».
4. Дублирующий запрос с `idempotency_key` не создаёт повторное событие или расход.
5. Конкурентные решения на одной версии не затирают друг друга; оптимистическая блокировка либо транзакционная проверка `seq`.
6. После рестарта сервера события и текущий статус восстанавливаются одинаково.
7. Времена `occurred_at` и `recorded_at` хранятся отдельно; отображать Камчатку (`Asia/Kamchatka`) при нужной локали.
8. Правка файла или записи в БД задним числом должна быть обнаружима или запрещена на уровне приложений и доступа; приложение не обещает криптографически защищённую неизменяемость без отдельной инфраструктуры.

## Минимальные acceptance tests

- [ ] Пользователь без полномочий не выдаёт/не принимает наряд, даже подставив поле роли в запросе.
- [ ] Подрядчик не видит документы и заказы другого подрядчика без явного разрешения.
- [ ] `accepted` нельзя установить из `draft`, `issued` или `reported` в обход проверки.
- [ ] Две одновременные попытки перехода по одной версии: одна проходит, вторая получает конфликт.
- [ ] Повтор идентичного HTTP-запроса с тем же ключом не создаёт дубликат.
- [ ] После рестарта и миграции на существующей БД нет потерь; миграция повторно исполняется безопасно.
- [ ] При отклонении/споре исходная цепочка сохраняется.
- [ ] Удалённые/неподдерживаемые вложения не превращаются в принятый доказанный результат.
- [ ] `npm test`, `npm run build`, `npm run demo` проходят; UI без нового поля также работает.

## Границы MVP

Не интегрировать КЭП, ЕИС, бухгалтерию и реальные персональные данные в первый шаг. Сначала безопасный серверный журнал с демонстрационными субъектами/ролями, затем согласование полей с заказчиком. Требования 152-ФЗ, хранения документов и электронной подписи до реального внедрения уточнить у профильных специалистов.
